# 店铺内咨询：店铺来自页面，订单来自消息或卡片

当前还支持“我买的耳机发货了吗”等商品名称问法，见[按商品名称咨询订单](product-order-lookup.md)。下面保留早期V3阶段的接口与订单号查询说明；最新会话、知识与商品定位以各模块文档为准。

用户进入店铺100，点击客服，再问“SF10001发货了吗”。
页面已知道正在咨询哪家店，不应要求用户再输入商铺ID。
本次完成后端的店铺上下文、订单查询和可选订单数据，前端可按协议渲染卡片。

## 请求和响应

新入口：POST /api/v1/shops/{shopId}/chat/messages。
shopId由店铺页面构造进URL，买家身份由登录认证提供。
继续使用已有HTTP Basic和CSRF，根目录chat.http已更新示例。

自然语言请求无需商铺参数：

```json
{ "message": "帮我看看SF10001订单发货了吗？" }
```

URL为/api/v1/shops/100/chat/messages时，后端只查询当前买家在店铺100的订单。
模型只提取订单号，没有商铺或买家字段；消息中的其他商铺ID不能改变本次查询范围。

点击订单卡片，或从订单详情页发起咨询：

```json
{ "message": "咨询此订单", "orderNo": "SF10001" }
```

该请求直接查询，不调用模型。orderNo仍是不可信定位参数，必须和当前店铺、
认证买家一起重新查询，不能因来自卡片就省略归属检查。
选中订单后继续问“发货了吗”时，每条请求都携带orderNo；
模型识别为查单但没有提取到订单号时使用该字段，消息明确的新订单号优先。
普通问候不会因为有选中订单就读取数据。本阶段没有跨消息记忆或会话表。

响应保留reply，并增加字段：

| 字段        | 含义                                            |
| ----------- | ----------------------------------------------- |
| type        | TEXT、ORDER_DETAILS或ORDER_SELECTION            |
| orders      | 公开OrderResponse列表，供前端显示详情或选择卡片 |
| nextAfterId | 下一批游标，没有更多时为null                    |

TEXT的orders为空；ORDER_DETAILS含一笔实际订单；
ORDER_SELECTION含当前店铺本人订单。卡片只包含商铺、订单号、状态、金额、
币种和时间，不公开内部主键、买家ID或历史客户ID。
数字游标用于定位下一批，不是身份凭证。

## 没有订单号时

模型识别到查单意图却没有订单号时，后端读取当前店铺本人订单并提示：

> 请选择当前店铺的一笔订单，或输入订单号。

前端可以根据orders显示可选卡片，纯文本客户端也可读取reply中的列表。
“查订单”和“我的订单”直接返回可选订单，模型关闭或故障时仍可使用。
首次没有订单时返回“你在当前店铺暂无订单。”，不会追问商铺ID。

固定查单格式现在是“查订单 SF10001”。旧格式“查订单 100 SF10001”返回400，
提示“查单格式：查订单 <订单号>，商铺由当前咨询页面确定”。
自然语言如“查订单，SF10001发货了吗”或“我的订单发货了吗”仍可交给模型。

## 一条消息经过哪些类

1. ChatController接收URL中的shopId、认证principal和ChatRequest。
2. ChatService先处理固定指令或卡片选择，自然语言交给OrderIntentRecognizer。
3. DeepSeekOrderIntentRecognizer通过HTTPS发送系统规则和消息，只接受intent、orderNo两个JSON字段。
4. ChatService将URL店铺、可信买家身份及订单号传给OrderQueryService。
5. 订单服务检查ORDER_READ，仓储通过JDBC用店铺、买家和订单号查询MySQL。
6. 结果组成ChatReply，再由ChatResponse.from映射公开DTO并序列化成JSON。

第3步和第5步分别访问外部模型和数据库，其余主要是同一JVM内的方法调用。
模型看不到服务端认证身份、权限或数据库订单结果。

| 类或方法                 | 输入                            | 输出与职责                         |
| ------------------------ | ------------------------------- | ---------------------------------- |
| ChatRequest              | message、可选orderNo            | 接收消息与所选订单，校验格式和长度 |
| ChatService.reply        | 身份、URL店铺、消息、所选订单号 | ChatReply，组织查询和选单流程      |
| OrderIntent              | intent、orderNo                 | 模型识别结果，没有商铺和身份       |
| listOwnedOrdersInShop    | 身份、店铺、游标、批量大小      | OrderPage，按店铺与买家取候选订单  |
| findByShopAndBuyerId     | 店铺、买家、游标、读取上限      | SQL层过滤后返回订单                |
| ChatReply、ChatReplyType | 文字、类型、订单、游标          | 区分文字、详情和选单的应用层结果   |
| ChatResponse.from        | ChatReply                       | 将领域订单映射为公开OrderResponse  |

## 翻页、安全和兼容性

- 每批最多20笔，多读1行判断下一批，游标取实际返回的最后一笔。
- 每页SQL同时包含buyer_id、tenant_id和id游标，不能跨店读完后再用Java过滤。
- 进入其他店铺会使用另一个URL；正文、查询参数、请求头和模型输出不能覆盖当前URL的店铺。
- shopId只是定位条件，可见性始终由认证买家和订单归属共同决定。
- 当前没有店铺目录模块；合法店铺ID无本人订单时返回空列表，详情无归属或不存在统一404。
- 缺ORDER_READ不能读取详情或候选订单；匿名、CSRF、非法路径和消息校验继续生效。
- 账户GET /api/v1/orders保留本人跨店订单列表，与店铺内客服区分。
- 旧POST /api/v1/chat/messages退役，已认证且CSRF有效时返回400及“请从店铺页面进入客服”，不执行查询或模型调用。
- 本次不包含店铺页面或聊天前端，接口已经提供渲染订单卡片所需的数据。
