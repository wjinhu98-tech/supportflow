# 在聊天里查看“我的订单”

## 用户现在可以做什么

发送 `我的订单`，查看当前登录买家在不同商铺的订单，每批最多20笔。
已有的 `查订单 100 SF10001` 仍然查单笔；普通消息仍然回显。

请求继续使用 POST /api/v1/chat/messages，认证及 CSRF 要求不变：

```json
{"message":"我的订单"}
```

这条消息不指定买家。服务端根据认证成功的账号确定“我”是谁。
例如当前买家有21笔订单，第一批只展示20笔，回复末尾可能是：

```text
还有更多订单，请发送：我的订单 2020
```

这里的2020仅为示例；实际数值由查询结果决定。复制整条指令继续：

```json
{"message":"我的订单 2020"}
```

这不是“第2020页”，而是“从上次返回的最后一笔订单之后继续查”。
不要自行加一，否则可能跳过订单；不需要手工猜测这个值。
每批显示序号重新从1开始。最后一批以“没有更多订单。”结束。

首次查询没有订单时，回复“暂无订单。”；非零游标之后没有订单时，回复“没有更多订单。”。
出现读取异常时返回错误，不会伪装成空列表。

## 一条消息经过哪些代码

1. 安全过滤链先认证账号并校验 CSRF；ChatController 获取可信身份和消息。
2. ChatService 将消息交给 OrderListCommand，得到 afterId；省略游标就是0。
3. ChatService 用当前身份、afterId 和统一默认批量20，调用已有 OrderQueryService.listOwnedOrders。
4. 订单服务先经过 ORDER_READ 方法级权限检查，再让仓储按 buyer_id 和 id > afterId 查询。
5. 仓储按内部主键升序最多读取21行。订单服务只返回前20行，多读的一行用于判断还有没有下一批。
6. 有下一批时，服务把本批最后一行的ID作为游标；ChatService 格式化真实订单信息和下一条指令。
7. ChatController 返回 ChatResponse，Spring 将其转成带 reply 字段的 JSON。

如果只读到20行，就已经到末尾，不给出多余的翻页指令。
多读的第21行不是游标，也不能提前展示，否则可能造成漏单。

## 本次类的职责

| 类或方法 | 谁调用 | 输入 | 返回及作用 |
| --- | --- | --- | --- |
| OrderListCommand.parse | ChatService | 消息字符串 | Optional<OrderListCommand>；提取非负游标，不查库 |
| ChatService.reply | ChatController | 可信买家身份、消息 | 回复字符串；区分列表、单笔和普通消息 |
| OrderQueryService.listOwnedOrders（已有） | ChatService、原订单列表入口 | 身份、游标、批量大小 | OrderPage；判断下一批，执行订单读取权限规则 |
| 仓储 findByBuyerId（已有） | OrderQueryService | 买家ID、游标、读取上限 | SupportOrder列表；用参数化SQL访问数据库 |
| InvalidChatCommandException | 两个指令解析器 | 对应的格式提示 | 由已有异常处理器转为400及枚举错误码INVALID_ARGUMENT |

ChatService 返回的是文字，不是数据库连接、实体列表或者新的HTTP接口。
它使用订单状态枚举提供的展示文字；订单金额来自实际结果，保留小数精度。

## 安全和行为边界

- 每次翻页都是一次新的请求，重新认证和授权。身份来自认证结果，不能从消息、请求参数或请求头指定。
- 复制别人的游标也不会扩大权限；仓储仍然限定当前买家。手动改大游标可能跳过自己的订单，但不能查看别人的订单。
- 沿用已有数字游标协议，它包含内部主键数值，不是保密令牌或身份凭证。不能把“知道游标”当作授权条件。
- 每批大小只使用 OrderQueryLimits.DEFAULT_PAGE_SIZE，不允许从聊天消息任意放大。
- 去除首尾空白后，以“我的订单”开头的消息保留为列表命令。负数、溢出、非数字或额外字段返回400并给出格式提示。
- 合法游标范围为0到Long.MAX_VALUE；0与省略游标等效，字段间允许多个空白。
- 不提供“下一页”这种依赖历史上下文的命令，不保存聊天记忆。必须复制完整的“我的订单 游标”。
- 回复展示商铺、订单号、状态、金额和币种，不展示买家ID或历史客户ID；不包含总订单数。
- 沿用已有内部主键升序，不承诺“最新订单优先”，也不是跨请求一致性快照；翻页期间数据变化可能影响后续结果。
- 未登录但携带有效CSRF的请求返回401；已登录却无ORDER_READ返回403；缺少CSRF可能先返回403。
- 不接AI、不新增表、不修改原订单查询服务、仓储、认证或授权规则。

## 怎样验证

在项目根目录运行 `mvn -o verify`，不需要执行 clean。
离线模式要求所需Maven依赖已经下载，容器测试要求Docker可用。

- OrderListCommandTest：覆盖默认游标、空白、合法上界、非法格式和非列表消息。
- ChatServiceTest：覆盖可信身份与统一批量传递、真实订单转文字、游标原样传递、空结果、权限异常和数据库异常。
- OrderApiIT：经过真实Spring安全链与Testcontainers MySQL，覆盖跨店本人订单、20+1翻页、恰好20笔、空列表、复制他人游标、身份伪造、401、403和CSRF。
- 原有单笔查单、普通消息和订单HTTP接口测试继续运行。

自动化测试使用独立临时数据库和随机凭据，不导入.local配置，不访问日常业务库。
根目录chat.http包含手工示例；其中订单和游标示例不保证存在于本地业务库。
