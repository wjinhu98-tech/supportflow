# 退款原因表单与售后期限

## 买家的操作

买家进入店铺、选中订单后，说“申请退款”“将该订单退款”或点击退款入口，会打开原因表单，而不是要求买家记住一条聊天命令。

```text
提出退款 → 选择本店订单 → 后台查询售后资格 → 填写退款原因
  → 买家确认提交 → 后台重新核验 → 待客服审核 → 现有演示退款流程
```

打开、填写或取消表单都不会创建售后申请。只有点击确认提交才会写入；页面不自动重放失败的提交。回复使用“待客服审核”等买家能理解的说法，不暴露编程语言、数据库表名、内部状态编码或模型工具实现。

退款原因先选择分类，再选择细分原因：

- 个人原因：不想要了；买错、多买或重复下单；尺寸或规格不合适；收货信息填写错误。
- 商铺原因：商品破损或有污渍；商品质量问题；商品与描述不符；发错商品；漏发或少发商品；未按约定时间发货。
- 其他：由买家填写具体情况，不能只输入空格。

页面不默认选中原因。切换类别或订单会清空先前选择及其他说明；选好细分原因，或填写有效的其他原因后，才能确认。分类仅记录买家的诉求，具体情况仍需客服核实。

接口仍使用现有的 `reason` 字段，保存完整文案，例如 `商铺原因：商品质量问题` 或 `其他：补充情况`，客服及历史记录都能看到分类与详情。总长度仍不超过500字符，其他说明最多497字符，预留“其他：”前缀的位置。选项与格式化规则集中在前端 `components/refundReasons.ts`，避免组件中散落原因文案。

当前仍是演示环境，不接支付渠道，不承诺真实资金到账。

## 经确认的店铺规则

- 默认从订单系统记录的确认收货时间起算15天；到达截止时刻即结束，全部按UTC时间计算。
- `support_order.received_at` 是可信订单事实，不能由浏览器或模型填写，也不使用创建时间或修改时间冒充。
- 没有确认收货时间或收货时间异常的历史订单，标记为需客服人工核实；可以提交原因，但不等于资格已经确认或退款已经获批。
- 未付款、已取消的订单不接受新申请；不能访问其他买家或其他店铺的订单资格。
- 提交时再次核验，不能依赖几分钟前打开表单的结果，也不能依赖浏览器时钟。
- 记录申请当时的资格、检查时间、收货时间、截止时间和适用天数。及时提交的申请，不因客服处理较晚就自动失效。
- 同一订单已有申请时返回原记录，不重新创建或重写原原因；截止时间之后的网络重试也不会变成第二张申请。

天数由 `supportflow.after-sale.policy.window-days` 配置，默认15，范围1至365。调整规则时应一并更新版本化售后知识说明与测试，避免客户说明和实际判定不一致。

## 前后端约定

聊天新增 `AFTER_SALE_FORM` 类型，最多附带一笔已验证归属的订单，不会在引导阶段执行退款或创建申请。缺少订单号或存在歧义时让买家选择，不猜测订单。

`GET /api/v1/shops/{shopId}/orders/{orderNo}/after-sale-eligibility` 返回后台资格预览：

| 状态 | 含义 | 可提交 |
| --- | --- | --- |
| ELIGIBLE | 在确认收货后的期限内 | 是，仍需客服审核 |
| REQUIRES_REVIEW | 关键时间缺失或异常 | 是，由客服核实 |
| EXPIRED | 已到达或超过截止时刻 | 否 |
| INELIGIBLE | 未付款或已取消等状态不支持 | 否 |

`POST /api/v1/shops/{shopId}/orders/{orderNo}/after-sales` 只需要 `reason`（1至500字），返回售后单及申请时的资格快照。买家身份取自认证上下文，订单金额取自服务端，客户端传来的时间、身份或金额不参与判定。接口沿用身份认证、订单查询权限、CSRF和现有幂等、审计、审批限制。

## 数据升级与历史数据

V6只新增可空的收货时间及资格快照列，不修改V1至V5，不回填假日期，不重写历史申请。历史申请没有资格快照时显示为未记录，需要客服核实；原先已经审批的任务不会因升级重新执行。

集成测试使用一次性MySQL。浏览器测试专用启动器仅在隔离测试库设置明确的模拟收货事实：`SF10002` 为期限内，`PAGE-001` 为已过期，`SF10001` 保持时间未知。这些测试日期不写入日常业务库。
