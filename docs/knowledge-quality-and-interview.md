# 知识问答质量与可验证的面试能力

## 本轮业务目标

买家说“能放张祝福卡吗”，应能找到店铺发布的“贺卡”说明；没有资料或不能确定商品类别时，不应凭相近词编造答案。回答要简洁，来源标题、版本和完整原文可单独展开。恢复历史时，应看到当时的引用，而不是今天修改后的文章。

这是一轮有边界的词法检索与工程质量改进，不是向量检索、通用语义理解或自主多步 Agent。

## 请求与数据流

```text
买家消息 + 当前店铺 + 已认证身份
  → ConversationOrchestrator：业务事实查询优先，不能用 FAQ 替代订单
  → KnowledgeService：读取当前店铺已发布快照，过滤不可信业务声明
  → KnowledgeQueryExpansion：版本化、有限的同义表达归一
  → KnowledgeRetriever：候选过滤、去重打分、确定性排序，最多两条
  → KnowledgeAnswer：短摘录 + KnowledgeEvidence
  → ChatReply / ChatResponse
  → 聊天记录保存整份响应快照
  → Vue KnowledgeSources：默认折叠，按需展示当时原文，不重新抓取文章
```

同义归一只发生在检索内部，不修改用户消息、订单号、身份、店铺范围、幂等摘要或工具参数。检索资料不发送给外部模型。

## 公开响应契约

原有 `reply/type/orders/nextAfterId` 保留，新增可空的 `knowledge`：

```json
{
  "reply": "简短的资料摘录，保留必要限制条件。",
  "type": "TEXT",
  "orders": [],
  "nextAfterId": null,
  "knowledge": {
    "status": "ANSWERED",
    "sources": [{
      "sourceId": "kb-12345678-1234-1234-1234-123456789abc",
      "version": "v1",
      "title": "【演示】贺卡说明",
      "content": "当时已发布版本的完整原文。"
    }]
  }
}
```

- `KnowledgeStatus` 是显式枚举：`ANSWERED`、`NO_MATCH`、`UNAVAILABLE`，分别表示有依据、没有足够依据、资料读取不可用。后两者没有来源，不把故障伪装成无答案。
- `ANSWERED` 必须有 1–2 条唯一来源；来源 ID 不是链接或文件路径。标题最长240字符，正文最长16384字符。前后端都校验协议边界。
- 普通非知识回复为 `knowledge: null`。旧历史 JSON 缺少该字段时按 `null` 恢复，不虚构引用、不修改历史数据。
- 知识证据不能附到订单卡片、分页或退款表单上，避免混淆资料与真实业务结果。
- 来源正文保持原样，展示时按纯文本转义，不渲染 HTML，不跳转外链，不触发工具或业务操作。
- 每篇原文不超过900字符时完整引用，保留所有段落、否定和限制条件；更长时仅提示展开原文，不依靠有限限定词表删除段落，也不在半句话处截断而改变含义。例如“可以附赠”后面的“买满两件才可附赠”不能被摘掉。
- 关键词在NFKC归一后必须非空；写入边界也拒绝规范化后全空白的值。特殊空格不能因 `query.contains("")` 恒真而让无关文章匹配所有问题。检查归一结果不改写完整来源原文。

## 为什么采用这些设计

| 决策 | 更简单的方案有什么问题 | 当前取舍与验证 |
| --- | --- | --- |
| 引用结构化，正文与短答分开 | 把来源拼进字符串，前端要反向解析；恢复历史时容易丢失版本 | 不可变 record、显式枚举、字段边界、JSON往返与旧历史兼容测试 |
| 在 SQL 按店铺和发布状态过滤后才排序 | 全库检索后再过滤，存在跨店泄漏和候选污染风险 | 复用发布快照查询；隔离 MySQL 测试覆盖草稿、下线、跨店与跨买家 |
| 同义词表有界、有版本，类别不明确时保守处理 | 无限制扩词或只看“清洗”会混淆陶瓷、玻璃、衣物等对象 | 固定正负评测集，包含相似问题不应召回的案例；这不等同于通用语义检索 |
| 保存当次引用原文，不恢复时再查当前文章 | 商家改版后，同一段历史回答会悄悄变成另一份证据 | 直接保存响应 JSON；历史不重新检索，不调用模型，不重放业务写入 |
| 不对资料不足或故障调用模型补答案 | 模型可能把未确认的资料变成店铺承诺 | `NO_MATCH` 与 `UNAVAILABLE` 分开；无来源时不显示伪造来源卡片 |

当前每店最多100篇同时发布的知识，每次最多引用两篇。词法索引在有界语料上构建；没有共享索引或缓存，因此发布、下线可在下一次读取生效。数据量或并发增长后的CPU、分配与数据库读成本需要先测量，再决定索引、缓存或向量检索方案。项目没有测得的QPS、P95、成本或收益，不能写进简历当作事实。

## 如何复现验证

在仓库根目录运行后端全量验收（需要 Docker 提供一次性 MySQL，勿使用 `clean`）：

```powershell
mvn.cmd -o verify
```

知识质量的固定集、指标定义与针对性运行命令见 [`src/test/resources/knowledge-evaluation/README.md`](../src/test/resources/knowledge-evaluation/README.md)。固定集通过只代表这些已标注案例通过，不能据此声称开放域准确率100%或真实业务收益。

前端执行 `npm.cmd run check`、`npm.cmd run build`。真实浏览器使用 [`frontend/README.md`](../frontend/README.md) 的隔离后端，不对日常订单或售后数据做验收写入。

浏览器重点检查：同义问法命中、来源折叠和展开、HTML样例只显示文本、手机布局、文章下线后历史仍保留当时版本、无依据时没有来源卡片。历史快照会明确提示不代表资料当前仍有效。

本轮没有数据库迁移，不修改已执行的 V1–V11，也不扩大账号或店铺权限。

### 2026-10-25 最终验收

- 冻结源码后的 `mvn.cmd -o verify`：317项单元测试、240项一次性MySQL集成测试，失败、错误、跳过均为0，`BUILD SUCCESS`。
- 前端：TypeScript检查、336项单元测试、生产构建与完整格式检查通过。
- Edge：18项模拟接口测试、22项真实Java/一次性MySQL测试通过；检查了桌面与390px手机布局。真实浏览器覆盖同义问法、特殊空格拒绝、附赠条件完整保留、长文不截断承诺、来源纯文本展开及下线后的历史保留。
- 固定集：41条合成案例，期望来源总计21条、实际来源21条且全部正确，21条应拒答案例全部拒答。来源微平均precision/recall、拒答比例、原文快照一致性、店铺引用隔离比例在该集合均为1.0；不是未知问题准确率、线上质量或性能结论。
- 回归实际发现并修复了“公开费用关键词掩盖当前交易金额声明”“摘录丢失跨段购买条件”“NFKC归一后的空关键词误匹配”三类边界，没有通过删除失败案例提高指标。

测试业务写入仅发生在一次性数据库；日常部署核对采用GET，不发送聊天、申请、审批或订单变更请求，不新增演示文章，也不修改此前已发布的4条演示知识。知识检索链路不调用外部模型。

### 可以如何讲述这次设计

通俗解释：回答旁边保存一份“当时参考了什么”的证据；问法可以变化，但证据不足就不能装作知道。

项目代码对应：`KnowledgeQueryExpansion` 处理有限表达，`KnowledgeRetriever` 排序，`KnowledgeService` 生成摘录与证据，`KnowledgeEvidence` 约束结果，`KnowledgeSources.vue` 安全展示。

底层机制：有界集合与去重、确定性词法打分、不可变值对象、JSON兼容演进、数据库发布快照与按租户查询。不是依赖模型自行遵守提示词来实现权限隔离。

可据此组织自己的回答：这个模块解决了同义问法漏召回、原文堆积和历史引用漂移。选择有界词法扩展与结构化快照，是因为当前语料小且需要离线、可重复验证；代价是覆盖有限，不能处理任意语义。进一步升级应先用独立评测集比较召回与误召回，再衡量延迟、成本、隐私和权限约束。未实际参与和掌握的部分，不应声称是个人独立成果。

可继续准备的追问：

1. 为什么不直接接入向量库？什么规模或评测结果会让你改变选择？
2. 知识下线后，历史记录为什么仍能显示？如何向用户说明时效性？
3. 如果资料库不可用，为什么不能让模型凭常识继续回答店铺政策？
