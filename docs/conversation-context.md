# 受控话题与追问

用户查过订单后问“那物流呢”，系统可以根据上一轮已验证的订单号重新查询；用户问过某篇店铺资料后说“它怎么使用”，系统可以按资料 ID 重新读取当前发布内容。这里保存的是有限的话题引用，订单状态、权限、知识原文和业务决定都需要重新获得。

本实现沿用现有单体与会话表，没有新增迁移或数据库授权。它支持规则范围内的追问，不提供完整 LLM 长期记忆、任意代词理解、历史摘要或向量 RAG。

## 话题保存什么

`ConversationContextRef` 是服务端生成的公开值对象，通过 `ChatResponse.context` 返回，并作为成功客服回复 JSON 的一部分保存。

| `kind` | `orderNo` | `sourceIds` | `expiresAt` | 用途 |
| --- | --- | --- | --- | --- |
| `NONE` | `null` | `[]` | `null` | 没有可以继续引用的话题 |
| `ORDER` | 一笔合法订单号 | `[]` | UTC 到期时间 | 提供待重新核验的订单目标 |
| `KNOWLEDGE` | `null` | 1–2 个不重复的公开来源 ID | UTC 到期时间 | 提供待重新查找的资料目标 |

订单号最多 64 个字符，不能有空白或控制字符；来源 ID 使用与知识证据相同的格式。引用不包含买家身份、授权标记、旧订单状态或可直接执行的工具参数。买家始终来自认证主体，店铺来自当前请求路径。

形成新的已核验话题时，服务端设置 30 分钟到期时间。使用引用前校验到期时间，已过期或到期时间超出允许范围的引用不参与追问。问候等普通文字回复可以保留仍有效的引用，但不会刷新它的到期时间；只有实际查询形成新话题时才产生新的有效期。旧回复缺失 `context` 或为 `null` 时按空话题兼容，不向更早回复搜索可用订单。结构非法的响应会被前端协议校验拒绝，不会当作有效话题继续使用。

## 一条消息怎样流动

```text
用户发送消息（可明确选订单，可要求 resetContext）
  → App.vue / useSupportDesk：构造当前请求，保留待发送清除标记
  → ApiClient：认证 + 新 CSRF → POST 会话消息
  → ConversationController：取得认证买家、店铺与请求 DTO
  → ConversationService
      → JdbcConversationStore.reserve
          校验本人会话、检查请求键、预留轮次、读取最后成功引用
      → 事务外 ConversationContextEngine
          明确本轮目标，判断是否允许引用；不明确则澄清
          ├─ 订单：OrderQueryService 核验归属 → 原编排器/工具查实时数据
          └─ 知识：KnowledgeService 按当前店铺重新读取发布资料
      → JdbcConversationStore.succeed
          同一事务保存用户消息、回复 JSON/context、成功轮次状态
  → ConversationTurnResponse
  → useSupportDesk：更新当前话题和本轮新查询的订单卡片
  → ConversationContextNotice：显示话题、过期或清除待发送提示
```

`reserve` 与 `succeed` 分别使用短事务。模型或工具调用发生在两者之间，会话数据库行锁不会跨越模型 HTTP 等待。这里没有对吞吐、延迟或锁等待作性能承诺；这些结论需要针对部署环境测量。

## 订单、知识和业务写入各走什么规则

本轮明确的订单目标优先参与处理。对“这单状态”“那物流呢”等受限只读追问，`ConversationContextEngine` 才能使用有效 `ORDER` 引用；每次先用当前认证买家、当前店铺与订单号重新核验归属，再通过现有业务服务或工具取得最新数据。记住订单号不会让另一位买家或另一个店铺获得权限，旧卡片里的金额、状态也不会成为本次查询结果。

当前明确提出的新知识主题可以替换旧订单或旧知识话题。对能够确定为知识追问的消息，服务端按来源 ID 读取当前店铺已发布版本；公共资料也按当前目录解析。资料重新发布后，新回复使用新版本；已下线、无匹配或读取失败时不使用历史原文补答案。上一轮若有两个来源，而当前“它”指代不明，则要求用户明确资料主题，不任选一篇。超出受限规则的指代同样要求澄清。

例如，查过订单后问“这个礼盒多少钱”，只要本轮明确的是礼盒等公开商品或费用主题，就检索当前知识；无依据时澄清，不返回旧订单金额。泛指“这个多少钱”可以衔接当前订单，而“这单实付多少”“订单总价”始终走真实订单查询。这里的区别由受限规则决定，不能据此宣称理解所有自然语言表达。

退款、收货确认、审批、支付等敏感或写入意图不会从历史引用补订单参数。它们保留现有显式输入、归属与业务校验、确认表单和人工审批路径。用户在当前界面主动选单可以提供本轮 `orderNo`；服务器从历史记住的订单号不能替代这一步，更不能替代提交或审批同意。

历史记录仍保存当时的公开订单卡片和知识来源原文，方便回看依据。GET 历史不调用模型、检索或业务工具，不重放写入。前端恢复历史只显示话题提示，不自动选中历史订单或打开退款表单；展开历史来源只展示当时的快照，不额外抓取当前文章。

## 清除话题什么时候生效

会话消息请求支持布尔值 `resetContext`，缺省为 `false`。例如在下一条消息中清除旧引用，同时明确新订单：

```json
{
  "clientMessageId": "00000000-0000-4000-8000-000000000004",
  "message": "咨询此订单",
  "orderNo": "SF10002",
  "resetContext": true
}
```

服务端对这一轮从空话题开始，再按本轮明确输入处理，因此成功回复仍可能建立新的订单或知识话题。重置不表示禁止建立新话题。

点击前端“清除话题”或取消选单时，只清除界面选择并保留待发送标记，不立即 POST。页面提示“下一条消息不沿用上次话题”；下一条成功消息才将结果写入数据库。发送失败或结果不明时保留标记，避免下次悄悄沿用旧引用。发送前刷新页面、切换会话再返回，可能重新显示服务器尚未清除的旧话题；这是延迟到下一轮保存的明确取舍。切换账号、店铺或开始新会话时，该界面标记不会串到其他会话。

前端也会标明到期并移除同号旧选单，避免继续自动传它的 `orderNo`；用户主动重新选择仍会触发新查询。浏览器时钟只影响提示，最终是否可引用仍由服务器判断。

## 成功、失败与并发怎样影响话题

话题没有独立提前更新的存储步骤。`JdbcConversationStore` 在锁定本人会话时，读取最后一条成功客服回复 JSON 的 `context`；成功完成时，将新引用与该轮双方消息原子保存。保存失败会回滚这一轮，也不会留下“回复没保存、话题却前进”的中间状态。

| 场景 | 服务端结果 |
| --- | --- |
| 新消息处理并成功提交 | 新回复及其话题成为最后成功轮次 |
| 工具、模型或保存失败 | 不保存半对正常消息，最后成功话题保持原样 |
| 相同消息 UUID、相同请求内容重放 | 返回原轮次缓存，不重跑引擎，不覆盖较新的持久化话题 |
| 相同消息 UUID 改变内容或 `resetContext` | 请求摘要不同，返回冲突 |
| 同一会话已有有效处理中轮次 | 新轮次返回冲突，不并行更新该会话话题 |
| 处理租约过期、旧执行稍后返回 | 旧轮次不能提交成功结果，不覆盖后来的新轮次 |

轮次租约目前为 120 秒，与话题 30 分钟有效期是两个概念。租约控制正在执行的一轮能否提交；话题有效期控制后续请求能否解析引用。会话请求幂等不代表退款、支付等外部业务具有全局 exactly-once 保证，业务写入仍依赖各自的权限、事务、状态机和幂等设计。

## 类和接口各负责什么

| 类或接口 | 输入与返回 | 谁调用、调用谁 |
| --- | --- | --- |
| `ConversationController` | 认证主体、路径和 `ConversationMessageRequest` → `ConversationTurnResponse` | 接收 HTTP，调用 `ConversationService` |
| `ConversationService` | 买家、店铺、会话和本轮请求 → 已保存轮次或缓存结果 | 调用存储接口预留，事务外调用引擎，再完成或标记失败 |
| `ConversationStore` | 预留、保存、失败标记等存储操作 | 服务依赖的接口，由 `JdbcConversationStore` 实现 |
| `JdbcConversationStore` | 认证身份范围、请求/响应 DTO → 轮次与历史 DTO | 校验数据库归属，管理短事务、租约、请求摘要和 JSON 快照 |
| `ConversationContextEngine` | 当前请求、认证主体、上次引用 → 带新引用的 `ChatResponse` | 调用路由器、知识服务、订单查询服务和现有编排器；不直接持久化话题 |
| `ConversationContextRef` / `ConversationContextKind` | 校验后的引用值 / `NONE、ORDER、KNOWLEDGE` | 表达引用结构及有效期，不执行查询或授权 |
| `ConversationLimits` | 共享常量 | 提供话题 TTL、处理租约及消息/分页边界 |
| `KnowledgeService` | 店铺、问题和来源 ID → 带当前证据的回答 | 重新读取当前发布资料或公共目录，不以历史快照作为新答案依据 |
| `OrderQueryService` | 当前买家身份、店铺与订单号 → 本人订单 | 在引用被使用前重新核验订单归属，复用现有仓储读取 |
| `ApiClient` | 本轮界面输入 → HTTP 请求/校验后的 DTO | 检查引用形状与时间格式，按请求对获取 CSRF；不决定业务权限 |
| `useSupportDesk` | 用户事件与 API 结果 → Vue 响应式状态 | 管理待发送重置、话题到期提示、选单及异步响应隔离 |
| `ConversationContextNotice.vue` | 引用、过期/待发送/禁用状态 → 话题提示与清除事件 | 由 `App.vue` 展示，不读取业务数据或执行写操作 |

## 面试时怎样解释取舍

可以从需求开始：“用户希望接着问上一笔订单或上一篇资料，但不能把历史状态当最新事实，更不能让‘刚才那单’直接成为退款授权。”随后按引用解析、实时核验、成功轮次保存三步说明实现。

- 保存短引用，使跨请求的目标可恢复，并且能够限制有效期和结构。限制是只能覆盖明确规则内的追问，不能声称解决任意自然语言指代。
- 每次重新读订单和当前发布资料，使新回答遵守实时归属、版本和下线状态。代价是仍有数据库读取，不能把话题存储称为业务数据缓存。
- 与回复 JSON 同事务保存，复用原有表和成功轮次顺序，不需要额外迁移。代价是读取最后响应 JSON，未来若要做复杂检索、保留策略或大规模会话分析，需要重新评估存储设计。
- 一会话只允许一个有效处理中轮次，用冲突和租约明确并发顺序；模型调用在事务外。代价是同会话并行发送会冲突，且超时可能出现需要核实的结果，不能宣称全局 exactly-once。
- 清除标记随下一条成功消息保存，避免点击清除时增加隐式网络写入。代价是发送前刷新可能恢复旧主题，界面必须说明，而不能承诺已经永久清除。
- 没有把整段历史作为模型记忆，也没有加入向量数据库。要扩展完整多轮对话、摘要或语义检索，应分别设计评测、授权边界和版本失效策略，不能仅增加一个“memory”字段就认为完成。

验证应分别覆盖引用结构、订单实时变化与越权、资料更新/下线、多来源澄清、过期、重置失败保留、幂等缓存、并发及租约，以及历史恢复不产生业务写入。具体测试结果以本轮统一验收记录为准。
