# 买家删除已结束订单

买家可从自己的订单卡片删除已完成或已取消的订单。服务端保存一条不可变的删除记录，让订单从该买家的订单列表、按订单号查询、商品候选及聊天查单路径中隐藏。原订单、售后、执行结果和审计仍保留，商家的售后管理不受影响。

## 删除条件

- 身份必须为买家，具有既有`ORDER_READ`权限；店铺和买家归属由后端核对。
- 仅`COMPLETED`或`CANCELLED`订单可删除。未付款、待发货和已发货订单不能以删除代替取消交易或确认收货。
- 有`PENDING_REVIEW`售后申请时不能删除。已批准的售后只有执行成功才算结束：任务缺失、待执行、执行中或失败仍阻止删除；已拒绝或执行成功的售后不阻止。
- 页面需要二次确认。前端按钮只作提示，后端在事务中重新核实状态和待处理售后。

同一买家重复删除已隐藏订单返回成功，不重复写删除记录。对其他买家或其他店铺的订单统一返回不存在，不能通过猜测订单号删除别人的记录。商家账号不能使用买家删除接口。

## 接口与数据流

```text
买家订单卡片 → 确认删除
  → DELETE /api/v1/shops/{shopId}/orders/{orderNo}
  → 认证、BUYER类型、ORDER_READ和CSRF校验
  → 锁定本人订单，核实结束状态和售后处理情况
  → INSERT support_order_buyer_deletion
  → 204，前端移除候选并清除该订单的当前选择
```

接口成功为`204`，重复删除也为`204`；他人或跨店订单为`404`；状态不允许或有待处理售后为`409 ORDER_DELETION_CONFLICT`。浏览器不会因超时或网络中断自动重放DELETE，结果不明时先刷新订单列表核实。

V18新增`support_order_buyer_deletion`，按内部订单ID唯一记录店铺、买家、订单号、操作账号及UTC删除时间。应用只读取和插入，不能更新或物理删除该记录，也不增加对订单金额、归属等字段的写权限。这个操作是买家可见性的变化，不是永久清除历史业务记录；本轮不提供恢复入口。

旧聊天中的订单卡片是当时的快照，仍可回看。它不代表该订单现在仍可选；重新查单及其他业务操作仍须经过当前后端校验。删除不清空聊天或售后历史，不触发模型、退款或订单状态变化。

## 在本地启用

1. 用原迁移账号执行V18；V1–V17不变，不批量改动历史订单。
2. 管理员在已核对的本地`127.0.0.1:3306/supportflow_rebuild`执行[`config/order-deletion-runtime-grants.sql`](../config/order-deletion-runtime-grants.sql)全部内容：一条新表`SELECT, INSERT`授权及最后的`SHOW GRANTS`。
3. 保留本地账号和密码，更新并重启后端，前端刷新后使用。该脚本不属于Flyway，应用/迁移账号不能自行授权；不需要将root凭据写入项目。

Docker实验版由原`migrate → grant`步骤执行V18并追加新表INSERT权限，读取沿用原实验库SELECT权限。`LabDeploymentTool verify`检查新权限存在，且订单及删除记录都不能物理删除，删除记录不能修改；拒绝权限探测均带恒假谓词，不改变业务数据。

## 验收范围

隔离数据库测试应覆盖：结束状态可删除、进行中状态拒绝、待审核/待执行/失败售后拒绝、他人/跨店/商家拒绝、CSRF缺失拒绝、重复和并发删除不重复建记录、买家各条读路径隐藏、商家售后与原订单记录保留。前端测试覆盖取消确认、删除成功后清除选择、后端冲突提示及切店后过期请求不污染新页面。

日常数据库只迁移和追加所需权限，不以验证功能为由删除或隐藏已有演示订单。真实删除闭环在一次性测试数据库验证，不调用付费模型。
