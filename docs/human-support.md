# 转人工客服

买家在店铺聊天页点击“联系人工客服”，进入等待队列，可以先描述问题。拥有该店铺人工服务权限的商家客服接待后，在商家端回复。买家或接待客服结束人工服务后，买家可以继续使用智能客服。

人工消息只作为聊天内容保存和展示，不会被当作模型指令、退款审批或业务工具参数执行。人工服务期间，服务端拒绝同一买家、同一店铺的新智能回复，包括旧版无会话聊天入口和旧智能任务的恢复。结束人工服务会保留历史消息；发生转人工的会话在下一轮智能回复时不自动继承转人工前的结构化订单主题。其他旧会话各自保存的上下文不受此水位重置影响。

## 本机演示

1. 买家在普通浏览器打开 `http://127.0.0.1:5173/?shopId=100`，用原买家账号登录，点击“联系人工客服”并发送问题。
2. 商家在另一浏览器或隐私窗口打开 `http://127.0.0.1:5173/merchant`，用原 `support-reviewer` 账号登录，选择店铺 100 的“人工接待”。
3. 商家接待该咨询并回复，买家页面在下一次刷新轮询中显示“商家客服”的消息。
4. 任一端结束人工服务后，买家下一条普通聊天恢复智能客服。人工服务中的订单查看和退款申请入口仍可使用。

两个普通标签页共享浏览器登录会话，切换账号会让旧账号页面退出；双端演示需要独立的浏览器登录环境。账号原密码不变。

## 状态与权限

| 状态 | 买家 | 商家客服 |
| --- | --- | --- |
| `WAITING` 等待接待 | 发送问题、取消等待 | 查看待接待元信息，接待后才能读取人工消息 |
| `ACTIVE` 接待中 | 发送消息、结束人工服务 | 仅接待本人能读取本次接待的人工消息、回复和结束服务 |
| `CLOSED` 已结束 | 阅读历史、使用新申请标识重新申请 | 接待本人阅读本次接待记录，不再追加新消息 |

`CHAT_SUPPORT` 是独立权限。知识管理、售后审核权限不会自动赋予聊天接待能力。服务端每次检查账号类型、权限、当前有效员工身份及店铺授权；仅知道会话 UUID 不能读取其他买家、店铺或客服的对话。

商家接待页不提供该买家的订单、智能对话或其他人工接待记录。等待队列显示会话标识、状态和时间，不显示消息正文。已接待会话不允许其他客服读取、接管或回复；当前没有转接、强制接管或自动重新分配功能。如果接待账号停用或店铺授权被撤销，买家仍可主动结束服务并重新申请。

本地现有 `support-reviewer` 仅沿用已授权的店铺 100，不增加 101、102、103 的店铺授权。启用人工权限使用操作员连接执行 `LocalSecurityAccounts.java enable-chat support-reviewer`，只对已有有效商家员工绑定生效；密码不变，安全版本增加会使旧登录会话失效。

## 消息与并发

新申请使用独立 `requestId`，该标识在同一聊天会话内唯一；重复提交返回原申请，包括已经关闭的原申请。人工消息的 `clientMessageId` 在同一次人工接待内唯一：标识、发送身份和正文相同，返回已保存消息；改变正文或发送身份则返回冲突。结束服务后，同内容重试可以确认既有消息，但不能追加新消息。超时后界面先核对服务器状态，不自动重放写请求；明确重试保留原标识和正文。

消息只接受最多 2000 个字符的纯文本，拒绝 HTML 标签和除换行、回车、制表符之外的控制字符。界面以文本展示，不执行 HTML。当前不支持附件、富文本、已读回执或消息修改。买家可以分页读取当前聊天会话历次人工服务的消息；商家只能分页读取本人接待的那次人工服务。

同一买家和店铺最多一场正在等待或接待的人工服务。数据库唯一约束和统一的买家/店铺互斥范围共同保护这个规则；锁顺序保持一致。智能回复通过短事务获取处理权，在调用外部模型时不持有数据库事务。旧版聊天入口使用带令牌的短期租约，旧请求不能清除新请求的处理权，也不能在失去处理权后交付迟到回复。

尚未过期的智能处理任务会阻止转人工。申请人工服务时，过期的会话任务在同一处理权锁内标记失败，其迟到回复不能再写入聊天记录；旧版无会话入口会在返回前复核租约和人工服务状态。这里的过期处理不取消已经发出的模型请求，也不回滚此前通过独立业务接口提交成功的操作；订单和售后结果仍应从各自接口核对。

会话和消息均保存在 MySQL，重启后可以读取。人工消息不覆盖已有智能回复快照。记录按游标分页，每页最多 30 条；界面通过可见页面的定时刷新接收消息，切换店铺、退出或隐藏页面后停止相应轮询。这是轮询式接待模块，未实现 WebSocket、坐席排班或在线人数统计。

## 数据库和部署

V22 新增 `support_human_session`、`support_human_message`、`support_chat_scope`，以及账号人工权限和会话主题重置水位。迁移本身不创建人工会话、聊天消息或客服授权。

运行账号只需要：

- 接待表：`SELECT, INSERT, UPDATE`。
- 人工消息表：`SELECT, INSERT`，不能修改或删除历史消息。
- 智能/人工处理权表：`SELECT, INSERT, UPDATE`。

本机在迁移完成后，由 root 执行 [`config/human-support-runtime-grants.sql`](../config/human-support-runtime-grants.sql) 的全部语句。应用和迁移账号均不自行授予权限。

该脚本包含三个指定表的 `GRANT` 和一个 `SHOW GRANTS`，目标账号为 `'supportflow_app'@'127.0.0.1'`。它不授予账号表、商家员工或店铺授权表的写权限，也不授予人工消息的 `UPDATE`、任何表的 `DELETE` 或转授权能力。启用 `CHAT_SUPPORT` 仍需另行执行上面的操作员命令；重复启用不会再次增加安全版本。

隔离部署沿用 `migrate → grant → seed-accounts → backend` 顺序。账号准备步骤仅为既有 `lab-merchant` 启用人工服务，不创建运维业务账号或扩大店铺授权。

## 接口

买家入口为 `/api/v1/shops/{shopId}/chat/conversations/{conversationId}/support`，支持查询状态、申请、分页读取消息、发送消息和结束服务。商家入口为 `/api/v1/merchant/shops/{shopId}/support-sessions`，支持队列、详情、接待、发送和结束。所有写请求需要 CSRF，并沿用已有按认证身份的限流。

订单列表使用只读 `GET /api/v1/shops/{shopId}/orders`，不借用聊天入口，所以人工接待时仍能刷新本人在当前店铺的订单。它支持 `afterId` 和 `size` 游标分页，沿用原有订单归属和删除可见性校验。

订单确认收货、退款申请和商家售后审批继续走各自独立的业务接口。客服的一段聊天回复不能替代这些校验和审批。

隔离环境可执行 `node scripts/check-human-support-lab.mjs` 验证双端接待、重复消息、智能回复互斥和结束恢复。脚本只允许固定本机实验地址，只创建本次演示会话和消息，不删除记录、不修改订单或退款，也不调用付费模型。

## 本轮验证（2026-10-30）

- Java 单元测试 630 项通过。
- 11 组相关集成测试共 264 项通过，涵盖人工接待、并发与幂等、过期处理权、账号会话、迁移以及既有聊天、订单和知识功能。
- 前端类型检查、574 项单元测试和生产构建通过。
- Edge 模拟后端测试 31 项、真实 Java/MySQL 后端测试 30 项通过；包含人工等待时刷新页面、查看订单和退款表单、结束后恢复智能回复，以及订单删除后的只读刷新检查。
- 隔离部署的 12 项人工服务闭环检查、51 项部署检查和运行账号最小权限检查通过。
- 本地新连接复核三表精确权限、商家能力和原订单数据；自动验证没有创建日常人工会话、消息或修改订单。功能写入测试使用临时数据库或隔离部署。

这些批次验证的是已覆盖场景的行为；没有付费模型调用、真人客服排班、WebSocket 或完整生产容量测试。
