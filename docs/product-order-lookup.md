# 按商品名称咨询订单

用户进入店铺后，可以直接问“我买的那副耳机发货了吗”，也可以问“黑色耳机物流到哪了”。页面提供店铺，认证提供买家身份，后端根据购买时的商品名称和规格定位订单。订单号仍可用于精确查询，用户不必先记住它。

## 从一句话到订单

```text
“我买的那副耳机发货了吗”
  → 提取只读问题和字面关键词“耳机”
  → SQL 同时限定当前店铺、认证买家和购买时商品快照
  → 一笔：重新核验归属，查询当前整单状态
  → 多笔：显示名称、规格、数量、下单时间，等待用户选择
  → 没有匹配：提示换名称或从订单中选择，清除旧话题
```

当前物流按整单记录，没有商品级拆包发货数据，所以回复说明“包含这件商品的订单”的整单状态。不能据此承诺某一个商品独立发出、到达时间或退款到账。

正文里的明确订单号优先；没有正文订单号而明确提到新商品时，新商品优先于前端携带的旧订单号和会话里的旧订单。没有匹配不会回退查询旧订单。

“耳机一般多久发货”“耳机怎么保养”等公开问题继续查知识；退款仍要选订单、填写原因和人工审核。商品名称只用于定位只读查询，不构成退款申请或审批授权。

## 购买快照和历史数据

V16 为现有 `support_order` 添加 nullable `product_items_json`：

```json
[{ "productName": "蓝牙耳机", "specification": "黑色", "quantity": 1 }]
```

这是购买当时的客服订单投影，不随当前商品目录改名而变化。一笔订单最多保存20条，名称最多100字、规格最多80字、数量1–9999。历史 NULL 表示信息未知，不会按订单号或金额猜商品。

领域快照保留完整明细，公开订单卡片只预览前三条并返回 `itemKinds`，避免列表和历史消息无限膨胀。旧响应缺少商品字段时归一为空；前端继续显示原有订单信息。确认收货后的响应也保留购买快照。

已有订单表级 SELECT 授权覆盖新增列；应用账号不会获得商品信息写权限。迁移账号使用已有 ALTER 权限，因此本次不需要新的 root 授权脚本。

V17 在同一快照里增加可空的 `imageUrl`，以单个 ALTER 替换 JSON 校验约束，不修改 V16、不补写历史订单。旧三字段 JSON 和旧消息仍能读取。图片只允许同源 `/products/demo/` 下长度不超过240的 png/webp/jpg/jpeg 文件路径，不允许外链、查询参数或目录跳转。后端不会下载图片。

订单列表和聊天候选共用商品卡片，展示名称、规格、数量和缩略图；图片缺失或加载失败显示“暂无图片”。四件学习商品使用项目内的生成图片，角标标明“演示图”，不是实际商品实拍或品牌素材。图片文件与生成提示词见 [product-images.md](product-images.md)。

## 定位和选单规则

目前使用有界字面包含匹配，支持有限颜色前缀及名称、规格组合，例如“黑色耳机”“蓝牙耳机 黑色”。关键词2–100字、最多4个拆分词；过长或过宽的输入提示补充，不静默截断为更宽的查询。复杂问法和没有可靠商品信息的历史订单仍需要用户选单。

SQL 的相关标量子查询 `COUNT(*) > 0` 在同一条商品明细上匹配，每笔订单最多检查20项，避免同一订单重复出现，也不会把另一件商品的颜色凑成匹配。该写法规避 [MySQL 8.0 的 EXISTS/JSON_TABLE 半连接错误](https://bugs.mysql.com/bug.php?id=114897)。`%`、`_`、`!` 按字面转义，值通过参数绑定。读取最多21笔，展示最多20笔；超过时要求补充名称或规格，不使用会丢失商品过滤条件的普通订单翻页游标。

多笔候选返回 `ORDER_SELECTION` 和受限 `selectionIntent`：

| 值             | 用户选择卡片后发送的固定只读指令 |
| -------------- | -------------------------------- |
| `ORDER_STATUS` | `咨询此订单` + 所选订单号        |
| `LOGISTICS`    | `查物流` + 所选订单号            |

前端不会重放用户原文。恢复旧候选卡片时只允许查询最新订单，切店清空继续意图。无候选或带普通分页游标的响应不能携带继续意图。

唯一物流匹配复用现有持久化 Agent：原始请求保持不变，服务端解析的订单号单独保存，继续执行白名单、归属校验、预算、重试和 Checkpoint。恢复时沿用原已解析订单并重新核验归属，不因后来新增同名商品订单而换单。

| 店铺           | 订单     | 商品                |
| -------------- | -------- | ------------------- |
| 102 数码优选店 | SF102001 | 蓝牙耳机，黑色      |
| 102 数码优选店 | SF102002 | 无线鼠标，白色      |
| 103 生活家居店 | SF103001 | 陶瓷马克杯，白色    |
| 103 生活家居店 | SF103002 | 棉质四件套，1.8米床 |

新建这四笔学习订单时包含快照。既有学习订单必须显式运行 `DemoProductData.seed(connection)`；它先核实全部订单归属、店铺和原始学习金额，只填 NULL，保留已有快照、状态、金额、收货时间、修改时间和商家授权。重复运行不会覆盖数据。

Docker 实验环境更新镜像和迁移后可执行：

```powershell
docker compose -p supportflow-lab -f deploy/compose.yml run --rm --no-deps migrate seed-products
```

这条命令只处理上述四笔已核实的学习订单。日常库通过固定本地迁移连接显式执行相同导入器。商家账号仍只管理店铺100，不因为新增商品而获得102/103权限。

应用 V17 并更新前后端镜像后，可以显式补齐这四笔学习订单的演示图片：

```powershell
docker compose -p supportflow-lab -f deploy/compose.yml run --rm --no-deps migrate seed-product-images
```

该命令在同一事务先核实并补齐缺失的学习商品快照，再为精确匹配的单项商品补图片；已有非空图片、自定义商品、空快照和其他订单均保留。它不改变订单状态、金额、收货时间、修改时间或商家授权。日常应用启动不会自动执行导入。

店铺100、101的10笔原始 `SFDEMO20261021*` 学习订单由独立的 `LocalDemoProductDetails` 工具显式补齐，映射和使用方法见 [local-demo-data.md](local-demo-data.md)。它不处理其他买家的订单，也不会把历史未知商品按订单号推测为真实购买资料。

## 主要实现

| 位置                                               | 作用                                                   |
| -------------------------------------------------- | ------------------------------------------------------ |
| `ProductOrderQuestion`                             | 区分商品只读问题、一般发货说明和没有商品称呼的物流追问 |
| `ConversationContextEngine`                        | 在旧选单和话题之前定位新商品，处理唯一、多笔和未命中   |
| `OrderQueryService` / `JdbcSupportOrderRepository` | 有界匹配，SQL限制买家和店铺                            |
| `OrderItemSnapshot` / `OrderResponse`              | 校验购买快照并提供有界公开预览                         |
| `OrderSelectionIntent`                             | 仅允许固定状态或物流继续操作                           |
| `OrderCard.vue` / `useSupportDesk`                 | 展示商品候选，点选后重新查询，安全处理旧记录           |

测试包括商品问法、公开问题和旧选单的区别，唯一/多笔/未命中，SQL同店同买家隔离、同项组合匹配、特殊字符和21笔上限，V15升级及旧SELECT授权、旧JSON兼容、人工审核边界、真实Agent查询与恢复，以及前端商品卡片和固定指令选择。
