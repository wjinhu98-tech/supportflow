# 会话与聊天记录

当前页面已升级为[V15 每店固定窗口与主动删除](shop-chat-windows.md)，会保留并汇总旧咨询。本页保留 V8 原会话 API 和快照机制的设计说明；当前界面不再通过“新会话”切开聊天记录。

## 范围

本模块在现有单体内增加店铺会话、双方消息和公开订单卡片快照。原无状态聊天接口继续用于后台加载订单等兼容场景，不会把这些请求写进会话。

历史模块负责保存、分页恢复与权限隔离。受控追问只读取最后一轮成功回复中的订单号或知识来源引用，不会把整段历史自动发送给 DeepSeek，也不增加自动退款、自动确认收货或后台通知。引用有效期为 30 分钟；重新使用时必须读取当前业务数据，详见[受控话题与数据流](conversation-context.md)。

买家重新打开页面后仍需连接账号；账号密码和认证头不保存在浏览器存储。认证成功后恢复当前买家在当前店铺最近创建的会话。点击“新会话”只是开始另一段聊天，不删除历史；首次发送时才创建新会话。

## 接口

所有会话接口都要求认证，POST 还要求 CSRF；买家身份只能从服务端认证主体获得。

| 方法与路径 | 作用 |
| --- | --- |
| GET `/api/v1/shops/{shopId}/chat/conversations` | 按创建顺序倒序读取本人在当前店铺的会话，每页20条 |
| POST `/api/v1/shops/{shopId}/chat/conversations` | 创建空会话，返回201和公开会话UUID |
| GET `/api/v1/shops/{shopId}/chat/conversations/{id}/messages` | 最新40条成功消息，页内正序；`nextBeforeId` 用于读取更早记录 |
| POST `/api/v1/shops/{shopId}/chat/conversations/{id}/messages` | 接收 `clientMessageId`、`message`、可选 `orderNo` 与可选布尔值 `resetContext`（缺省为 `false`），执行一轮并保存双方消息 |

两个列表均通过 `beforeId` 使用服务端返回的不透明UUID游标。读取其他买家、其他店铺的会话或游标返回404，UUID本身不代表访问权限。会话列表排序不随新消息移动，避免翻页期间出现重复或漏项。

## 一轮消息如何保存

1. 短数据库事务校验本人、店铺和会话，预留客户端消息UUID及请求内容摘要。在锁定当前会话时读取最后一轮成功客服回复的 `context`；缺字段或为空按 `NONE` 处理，不向更早历史寻找其他话题。请求要求重置时，本轮从空话题开始。
2. 释放事务和行锁后调用 `ConversationContextEngine`，按本轮显式目标、有效引用和规则决定重新查询或澄清，再复用现有编排器；模型HTTP等待不会占着会话数据库锁。
3. 成功后用另一个短事务原子保存用户消息、客服回复和包含 `context` 的响应 JSON；订单只存公开DTO，不存内部订单主键、认证信息或模型原始响应。新话题与新回复一起可见，不单独提前提交话题。
4. 异常不写入半对正常历史；失败/结果不确定的请求不会自动重新执行。正在处理的请求有120秒期限，后续新请求可结束过期占用，但同一失败请求ID不能重放。

同一客户端消息UUID和相同内容重复提交：已成功时只返回原保存结果，不再次调用编排器。相同UUID不同内容、仍在处理或失败的请求返回409。该设计不是支付或业务写入的全局 exactly-once 承诺；售后等业务仍使用各自的权限、事务与幂等校验。页面不会自动重试不确定的写操作。

`resetContext=true` 参与请求摘要，不能沿用同一消息 UUID 改变清除意图。缓存重放返回原轮次快照，不会再保存一次，也不会覆盖服务器上较新的话题。同一会话的有效处理中轮次阻止并发新轮次；租约到期后旧轮次不能提交成功结果。失败、回滚或过期迟到结果不会写入新的正常消息，也不会改变最后成功话题。

前端“清除话题”和取消选单只设置待发送标记，不立即 POST。下一条成功轮次才把清除结果（或该轮新建立的话题）保存；失败和结果不明时保留标记。发送前刷新或切换会话再返回，可能恢复服务器原先的话题，这与立即永久清除不同。

## 历史不是业务事实来源

GET 历史仅查询数据库，不经过编排器、模型或业务工具。因此刷新、切换会话、加载更早消息不会重新提交售后，也不会自动弹出历史退款表单。

历史订单卡片标明当时快照；再次咨询该订单必须重新走后端归属校验和实时查询。过往消息不能覆盖数据库中的当前订单状态，保存的文字和卡片也不被当作新的操作指令。

恢复历史可显示最后回复的 `ORDER / KNOWLEDGE / NONE` 话题提示，但不会据此自动选中订单或重开售后表单。订单追问每次核验当前认证买家、当前店铺及订单归属后查询实时状态；知识追问按来源 ID 重新读取当前发布版本，下线或不可用时不回退到历史原文。涉及多个来源又未明确目标时要求澄清。退款、审批、收货等写请求不会从历史话题补订单参数，仍要求当前请求明确选择和原有业务确认。

## 数据库与运行权限

V8 只新增 `support_chat_conversation`、`support_chat_turn` 和 `support_chat_message` 三张表，不变更旧迁移或历史订单。旧的浏览器内存聊天记录无法追溯恢复。

迁移由迁移账号执行。管理员随后手动执行 [`config/conversation-runtime-grants.sql`](../config/conversation-runtime-grants.sql)：会话和消息轮次允许SELECT/INSERT/UPDATE，消息表只允许SELECT/INSERT，不授予DELETE、DDL或其他业务表的新权限。应用和Flyway均不会自动执行授权脚本。

受控话题复用 `support_chat_message.response_json`，没有新增数据库表、字段、迁移或运行授权。历史 JSON 缺少 `context` 仍可读取；这不补造历史话题，也不重新执行历史消息。

这是学习版本的历史保留实现，暂不提供删除或归档API；生产上线前应明确保留期限、访问审计和个人信息管理规则。
