# Agent 故障治理：熔断与受控重试

V14 在现有只读订单 / 物流 Agent 上增加故障分类、一次受控重试和共享模型熔断。原始聊天 POST、退款申请、人工审批和退款执行不会因此自动重发。模型关闭时仍使用规则决策器。

## 一次请求如何流动

```text
预留步骤与模型预算 → 尝试模型 / 只读工具 → 成功则保存 Checkpoint
                                       ↓ 临时故障
                         保存失败类别与重试标记（短事务）
                                       ↓
                         检查原步数、期限、Token / 费用余额
                                       ↓ 允许且本步骤未自动重试
                         短暂等待 → 再预留一个步骤和模型预算
                                       ↓
                         再次尝试；仍失败则暂停，等待显式恢复
```

`operationId` 表示同一个逻辑步骤，`attempt` 表示一次尝试。不同观察轮次的 PLAN 各有自己的 `operationId`。同一逻辑步骤最多自动重试一次，标记在数据库中保存；重新创建 Java 对象、进程重启或人工恢复不会补回自动重试次数。显式恢复仍受原步数、期限和模型预算约束。

新运行创建时冻结重试规则。V12 / V13 已存在的运行通过迁移补为“自动重试关闭”，继续保留原来的恢复语义。新运行的默认配置是：

```yaml
supportflow:
  agent:
    retry:
      max-read-retries: 1
      delay: 250ms
  ai:
    deepseek:
      circuit:
        failure-threshold: 5
        open-duration: 30s
```

`max-read-retries` 仅允许 0 或 1，等待最多 1 秒。已经保存的订单或物流结果不会再次执行；重试前仍检查当前归属、步骤代次和租约。

## 哪些错误重试

| 故障                                             | 自动重试 | 后续行为                                       |
| ------------------------------------------------ | -------- | ---------------------------------------------- |
| 模型网络超时、已分类的 I/O 连接失败              | 最多一次 | 原响应计费可能不明，保留原预留，新尝试重新预留 |
| 模型 HTTP 500 / 502 / 503 / 504                  | 最多一次 | 经过同一个共享熔断与并发入口                   |
| 只读工具的 Spring 瞬时 / 可恢复数据访问故障      | 最多一次 | 仅在运行存储仍可用且能保存重试标记时继续       |
| 参数错误、无权限、订单不存在、伪造或重复工具     | 不重试   | 保留既有业务拒绝语义                           |
| 400 / 401 / 402 / 422、429、非法响应、缺失 usage | 不重试   | 返回安全提示；429 不立即冲击供应商             |
| 本地并发满、熔断拒绝、线程中断 / 取消            | 不重试   | 及时停止，不在本机等待队列中堆积               |
| Checkpoint 保存失败、提交结果不明或执行代次冲突  | 不重试   | 保留原恢复机制，不自动重新请求模型或业务工具   |

供应商错误分类参考[DeepSeek 官方错误码](https://api-docs.deepseek.com/quick_start/error_codes/)。重试只针对 Java 白名单中的已知故障，不通过异常文本猜测是否重试，也不记录供应商原文。

V2 Agent 每次模型 HTTP 请求的完整响应期限取“配置的单次期限、原运行剩余期限、当前租约剩余时间”中的最小值；其他模型入口继续使用配置的单次期限。前端聊天提交最多等待 105 秒，以覆盖后端最多 100 秒的运行期限；普通接口仍使用 25 秒。页面取消或网络超时后不会重放聊天 POST，仍通过只读记录核实结果。

本地订单和物流工具使用 JDBC 读取；Agent 在调用前和结果提交时检查总期限。这不等于给任意 JDBC 驱动提供强制中断能力，也不声称能取消已经到达供应商的模型计费。网络结果不明、本地限流及熔断拒绝对应的模型预算预留均保守保留，不能把 `chargedTokens` 当作供应商已确认账单。

## 熔断怎样恢复

所有三个 DeepSeek 入口共享一个进程内熔断器：意图识别、旧工具规划、多轮 Agent 决策。HTTP 执行器内部每次最多发一条请求，没有隐藏重试。

- `CLOSED`：正常放行，按完成顺序统计连续失败；成功后清零。
- `OPEN`：达到默认五次连续失败后暂停调用三十秒，新请求立即拒绝，不发 HTTP。
- `HALF_OPEN`：暂停期后只放行一个真实请求作为探测，其他请求继续快速拒绝；成功恢复，失败重新暂停。

超时、网络失败、供应商错误 / 限流和非法响应计入连续失败；本地容量满或用户中断不会作为正常关闭状态下的供应商故障。中断的恢复探测会释放探测资格并重新进入暂停期。使用单调时钟计时，代次标记阻止旧在途调用的迟到结果错误地关闭或污染新熔断周期。

这是一台应用实例内的保护。多实例部署时每台各自判断，重启会重置本机熔断状态；运行步骤、预算、重试规则和次数仍由数据库保留。当前未实现跨实例统一供应商限额或按 `Retry-After` 调度重试。

## 数据、监控与界面

[V14 迁移](../src/main/resources/db/migration/V14__agent_read_retry.sql)只给原两张运行表增加字段，继续使用 V12 的表级 `SELECT / INSERT / UPDATE` 授权，无须新增授权脚本。运行保存 `auto_retry_limit / retry_delay_ms`；步骤保存固定枚举 `failure_kind` 与 `retry_scheduled`。公开步骤进度增加 `failureKind / retryScheduled`，不暴露请求原文、身份 ID、Key 或供应商返回体。

| 指标                                                             | 用途                                             |
| ---------------------------------------------------------------- | ------------------------------------------------ |
| `supportflow_ai_calls_total{operation,outcome}`                  | 调用结果新增 `CIRCUIT_OPEN`；熔断拒绝也计数      |
| `supportflow_ai_call_duration_seconds`                           | 模型调用耗时；保留原并发与大小限制               |
| `supportflow_ai_circuit_state`                                   | 0 正常，1 暂停，2 恢复探测                       |
| `supportflow_ai_circuit_transitions_total{from,to}`              | 熔断状态切换次数                                 |
| `supportflow_agent_retry_decisions_total{phase,failure,outcome}` | `SCHEDULED / STOPPED`，区分安排重试与直接停止    |
| `supportflow_agent_step_duration_seconds{phase,outcome}`         | 逻辑尝试耗时，失败尝试包括保存标记及本次等待时间 |

指标只使用有限的固定枚举维度，不把订单号、用户、会话 ID、异常文本或 Key 放进标签。实验环境 Prometheus 增加“持续熔断”和“瞬时错误多次停止”两条告警，阈值用于本机学习环境，不代表生产 SLO。模型关闭时不会创建真实模型熔断指标。

用户只看到“智能服务暂时不可用，请稍后重试，或在订单页直接查看订单”。前端按固定 `MODEL_UNAVAILABLE` 错误码显示提示，仍不信任供应商错误文本；其他服务故障保留通用提示。聊天页没有增加管理面板，历史咨询入口继续隐藏。

主要实现位置：`DeepSeekCallExecutor / DeepSeekCircuitBreaker` 负责共享调用保护；`AgentLoopExecutor` 负责故障分类及受控继续；`JdbcAgentRunStore.retryStep` 负责短事务保存失败、核验额度和防止重复安排；`AgentRetryPolicy` 是创建时冻结的规则快照。

## 验证

- `DeepSeekCircuitBreakerTest`：单调时钟、单探测、恢复、连续失败归零、旧代次迟到结果。
- `DeepSeekCallResilienceTest`：三个入口共享熔断、拒绝时不发 HTTP、安全分类和剩余期限取消。
- `AgentLoopPersistenceIT`：实际 MySQL 中的模型 / 工具恢复、同一步骤只重试一次、预算不足时停止、保存失败不重放、旧执行者隔离，以及 V12 / V13 存量运行升级。
- 前端测试：合法的长运行不会在普通 25 秒期限被提前中断；模型故障提示使用安全固定文案；消息只提交一次。

自动化使用模拟模型响应或关闭模型，不使用真实 Key 产生付费故障流量，不将日常业务数据库作为失败注入对象。

2026-10-27 验收：完整后端 476 个单元测试、303 个集成测试全部通过；前端 414 个测试、TypeScript 检查和生产构建通过。六个浏览器用例验证正常导航、业务拒绝、模型故障提示及失败消息只读核实不重发。Docker 实验环境十五项 Agent HTTP 检查通过，创建一轮实验会话，业务写入零次、模型调用零次。

本地与实验库均已迁移到 V14，原有授权可继续使用；实验前后端健康，Prometheus 三条告警已实际加载。日常实例只做 GET 与数据库元数据验证，确认原知识发布、店铺和角色权限仍有效。
